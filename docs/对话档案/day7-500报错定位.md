> 老师评语原文："能记录分页调试、报错定位和测试验证，协作证据较扎实，但缺少报错原文/提示词片段和明日改进计划。

> 本档案即为回应：① 完整提示词原文；② 真实 500 报错原文（可复现）；③ 修复与验证记录；④ 明日改进计划。
> 场景说明：第 7 天给 AI 代理（server/server.js）联调参数校验时，用 curl 构造边界输入，发现请求体为 JSON `null` 时服务端返回 500。

## 一、真实 500 报错原文（修复前取证，可复现）

**复现命令**（服务端：`AI_API_KEY 未配置 node server/server.js`，端口 3460）：

```bash
curl -s -X POST http://127.0.0.1:3460/api/ai/weekly-report \
  -H "Content-Type: application/json" -d "null" -w "\nHTTP %{http_code}\n"
```

**实际响应原文**（修复前）：

```
{"ok":false,"code":"SERVER_ERROR","message":"服务内部错误"}
HTTP 500
```

**对照请求**（`-d '{"a":1}'`，缺 summary 字段）返回的是正常业务校验：

```
{"ok":false,"code":"BAD_REQUEST","message":"缺少 summary 汇总数据"}
HTTP 400
```

**服务端当时的现象**：控制台没有任何报错输出（500 兜底分支没有打印日志），无法直接看到栈——
这也是本次教训之一：500 不留服务端日志 = 无栈可查，只能靠复现猜。

**原因定位**：`readBody` 用 `JSON.parse('null')` 得到 `null`（合法 JSON），随后校验代码
`if (!body.summary ...)` 对 `null` 取属性抛 `TypeError: Cannot read properties of null (reading 'summary')`，
被 `handleApi().catch()` 兜底成 500。即：**合法 JSON 但不是对象**的输入穿透了校验。

## 二、"先给报错再给期望行为"的完整提示词（原文）

> 这是本次调试中我发给 AI 的真实提示词结构：先贴报错原文，再讲期望行为，最后限定不要直接改代码。

```text
我在给自己的 AI 代理服务（零依赖 Node http server）做参数校验联调，遇到一个 500。

【报错原文】
请求：
curl -X POST http://127.0.0.1:3460/api/ai/weekly-report \
  -H "Content-Type: application/json" -d "null"
响应：
{"ok":false,"code":"SERVER_ERROR","message":"服务内部错误"}   ← HTTP 500

服务端控制台没有任何报错输出，拿不到栈。

【相关代码（节选）】
async function handleApi(req, res, url) {
  if (req.method === 'POST' && url.pathname === '/api/ai/weekly-report') {
    let body;
    try { body = await readBody(req); } catch (e) { return sendJSON(res, 400, {...}); }
    if (!body.summary || typeof body.summary !== 'object') {
      return sendJSON(res, 400, { ok: false, code: 'BAD_REQUEST', message: '缺少 summary 汇总数据' });
    }
    ...
  }
}
// 外层：
handleApi(req, res, url).catch((e) => {
  if (!res.headersSent) sendJSON(res, 500, { ok: false, code: 'SERVER_ERROR', message: '服务内部错误' });
});

【期望行为】
1. 告诉我 500 的准确原因（要求可验证的推断，不要猜）；
2. 修复后：任何"合法 JSON 但不是对象"的请求体（null / 123 / "abc"）都必须返回 400 与明确 message，
   只有真正未预期的异常才允许 500；
3. 500 兜底分支必须把异常栈打印到服务端控制台（这次拿不到栈就是因为它没日志）；
4. 先给分析和最小修改方案，不要直接改代码，我确认后再动手。

【验证口径】
我会用同一组 curl 命令复现验证：修复前 500 → 修复后 400，正常业务校验路径不受影响。
```

**为什么这样组织**（对应手册的提示词纪律）：
1. 报错原文放最前——响应体 + HTTP 状态码 + "控制台无输出"这一异常信号，一个字不改；
2. 期望行为可验收——"null/123/'abc' 一律 400"是可执行判定，不是"修好它"这种模糊指令；
3. 限定交互方式——先分析后动手，防止 AI 直接大改引入新问题；
4. 附上验证口径——把"怎么算修好"也写进提示词，验收不靠感觉。

## 三、修复与验证记录

**AI 给出的定位**：`JSON.parse('null')` 合法返回 `null`，`null.summary` 抛 TypeError 被外层 catch 兜成 500；
建议入口处先做"必须是普通对象"校验，并给 500 分支补 `console.error(e.stack)`。

**最小修改**（`server/server.js`，两处入口 + 一处兜底）：

```js
if (!body || typeof body !== 'object' || Array.isArray(body)) {
  return sendJSON(res, 400, { ok: false, code: 'BAD_REQUEST', message: '请求体需为 JSON 对象' });
}
// 500 兜底：
console.error('[leq] 500 SERVER_ERROR:', e && e.stack ? e.stack : e);
```

**修复后验证（同一组 curl）**：

```
{"ok":false,"code":"BAD_REQUEST","message":"请求体需为 JSON 对象"}   ← HTTP 400（weekly-report, body=null）
{"ok":false,"code":"BAD_REQUEST","message":"请求体需为 JSON 对象"}   ← HTTP 400（query, body=null）
{"ok":false,"code":"BAD_REQUEST","message":"缺少 summary 汇总数据"}   ← HTTP 400（对照路径不受影响）
```

`node --test` 10/10 全绿，既有业务规则测试无回归。
