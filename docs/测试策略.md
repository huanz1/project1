# 测试策略（人工覆盖策略）

## 为什么由人点名规则
AI 若只接到"给所有接口写测试"的指令，通常产出一堆 `assertNotNull` 之类的弱断言——看起来有测试，实际什么都没验。
正确姿势（本项目采用）：**人先点名必须覆盖的 5 条关键业务规则，AI 再补全边界用例**。

## 运行方式
```bash
node --test          # 自动发现并运行 tests/ 下的用例
```
- 测试框架：Node 内置 `node:test`，零依赖、无需安装。
- 浏览器脚本 `js/storage.js` 依赖 `localStorage`，测试用 `tests/localStorage.mock.js`（内存版）注入，
  通过 `vm` 在沙箱中加载浏览器脚本，**不改动任何已上线代码**。

## 人工点名的 5 条关键业务规则

| # | 业务规则 | 用例 | 断言 |
|---|---|---|---|
| R1 | 首次初始化写入种子数据 | 清空后 init | 设备 6 台、预约 6 条且全 active；init 幂等不重复 |
| R2 | 同设备+同日+同时段重复预约判定冲突 | 对已有 active 预约再查 | `hasConflict=true`；`occupiedSlots` 含该时段 |
| R3 | 不同设备/日期/时段不冲突 | 换设备/日期/时段 | 三种情况 `hasConflict=false` |
| R4 | 取消后释放，已取消预约不再阻塞 | 取消一条预约 | 状态 `cancelled`；该时段从 occupiedSlots 移除；同时段可再约 |
| R5 | 新预约正确落库并变为占用 | 空闲时段 addBooking | 预约数 +1；occupiedSlots 含新时段；此时该时段冲突 |

## 边界用例（防止弱断言）
- R1 同时验证**幂等性**（重复 init 不重复写入），避免"初始化只跑一次"的隐性假设。
- R3 用 `e_other`（不存在设备）、`2099-01-01`（未来日期）、`sX`（不存在时段）三个维度，
  而非只测一个。
- R4 不只验证状态变了，还验证**时段真正释放 + 冲突解除**（这是取消功能的核心价值）。
- R5 验证"落库 → 占用 → 冲突"的完整因果链，而非只断言数组长度。
